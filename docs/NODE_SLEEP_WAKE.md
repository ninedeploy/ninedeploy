# Node scale to zero and wake (R2)

Status, 2026-11-02: design accepted. Step 1, the agent idle watch, is accepted: [CI 41498096715](https://github.com/ninedeploy/ninedeploy/actions/runs/41498096715) passed all 12 sealed serving-traffic cases. Those included a 62 s verified zero, a chained window that counted one request, and a proxy restart that ended coverage, with no window left open. The agent wake catcher and the panel's read-only idle scheduler are implemented; their source/runtime CI has passed; the durable panel authority foundation is implemented, while ordered sleep/wake effects and public status remain open. Node services still cannot sleep. Scale to zero (`sleepAfterMinutes`) runs on the panel host only. `lib/sleep.ts` refuses node services with "scale to zero runs on the panel host only for now", and [DEPLOYMENTS.md](DEPLOYMENTS.md) documents that limit. This document records why the panel-host mechanism cannot be reused on a node, the decisions that replace it, and the ordered steps with their acceptance.

## Why the panel-host mechanism does not carry over

- **Idle evidence.** The panel host counts requests from its own Traefik access log (traffic analytics). A node's access log never reaches the panel. The node serving-traffic windows used by RPS autoscaling ([NODE_RPS_AUTOSCALING.md](NODE_RPS_AUTOSCALING.md)) are bounded reservations of at most 60 s with gaps between them. A zero there proves only that window was idle, not the minutes before it. Sleeping on that would stop a service that is in use.
- **Wake path.** A sleeping panel-host domain routes to the panel's own wake endpoint (`/_nd/wake`, `modules/wake.ts`) over the local Docker network. On a node, the panel calls the agent and the agent never calls the panel. A node proxy cannot assume a route to the panel, and the panel's Traefik does not know node domains.

## Decisions

1. **Continuous idle watch (new sealed agent operations).** `proxy.idleWatch.open/sample/finish/close` is a separately advertised capability under the existing owner opt-in `NINEDEPLOY_AGENT_PROXY_TRAFFIC=on`. It reuses the serving-window engine with `purpose: 'idle'` and windows of 1 minute to 1 hour (`idleWatchOpen`). A window counts requests to the selected serving leaves continuously between its start and end sequence markers. The engine releases a window that is not sampled within 30 s, so the panel samples every 15 s; that is the lease. Because `sleepAfterMinutes` can reach 24 hours, the panel chains windows. It opens the next window before finishing the previous one, so the next start counter is below the previous end counter, and requires the same source, proxy and agent epoch. Overlapping chained receipts therefore leave no unobserved gap. A proxy restart, source change, routing change, lease lapse, agent restart or any refusal ends coverage, and the idle clock starts again. A service sleeps only after a verified zero count over continuous coverage of `sleepAfterMinutes`. Unavailable coverage never counts as idle, the same rule RPS uses.
2. **Node wake catcher.** The agent manages one fixed container per node, `ninedeploy-wake`, on the node's `ninedeploy` network. It runs from the agent's own pinned image with no host mounts and no Docker socket. It answers every request with the "waking up" page: `503` with `Retry-After` and a self-reloading HTML body, and `HEAD` works too. It records demand per opaque wake token taken from the routed path prefix. Tokens map to services on the panel only, so the catcher holds no service data. Demand is kept in memory, bounded and expiring.
3. **Routing.** A sleeping node domain routes to the catcher after the domain's own middlewares, so basic auth and IP allow lists still run before anything wakes, as on the panel host. Routes are written through the panel-rendered node dynamic config and confirmed with `proxy.routingAck` before any container stops.
4. **Wake.** For each node with sleeping services, the panel polls the sealed `wake.demand` operation every 2 s. On demand it acquires the service runtime owner and starts the recorded serving count by immutable ID through the ordered node lifecycle. It then waits for readiness, restores the routes with routing confirmation, and records `service.wake`. The visitor's page reloads into the app. A cross-host redirect is not used, because a non-GET body cannot be replayed anyway.
5. **Sleep effect order.** Sleep follows a strict sequence:
   1. reserve the runtime owner;
   2. switch routes to the catcher;
   3. confirm routing;
   4. stop the serving members by immutable ID with a sleep intent, distinct from Stop;
   5. record `service.sleep`.
   
   A failure at any step before the containers stop restores the routes, and the service stays awake.
6. **Authority.** Explicit Stop, deploy and Restart supersede sleep and wake, as on the panel host. The autoscaler holds while a node service sleeps; nothing sleeps during a deploy, canary or autoscale transition. Fan-out and Swarm services stay refused with their own reasons.

## Ordered implementation

1. Agent: the `proxy.idleWatch` contract and capability, on the bounded log transport and sequence markers. Cover lease lapse, restart, source change and refusal with tests, and add a hosted observation case (continuous zero, a single request breaks the zero, proxy restart resets coverage). *Implemented 2026-11-02:*
   - `lib/nodeIdleWatch.ts` and `agentOps/idleWatch.ts`.
   - Agent tests: `test/agentOps/idleWatch.test.ts` (two-minute verified zero under a 15 s lease, a single request, lease lapse, overlapping chain, owner disable).
   - Hosted cases in `scripts/fixtures/serving-traffic-agent.mjs`: a verified zero over one minute, a chained window broken by one request, and a proxy restart ending coverage.
   - The agent now also closes serving and idle windows when it shuts down.
2. Agent: the `ninedeploy-wake` catcher (an idempotent ensure/remove operation, pinned image, no mounts) and the sealed `wake.demand` operation. Cover token bounds, expiry and missing-catcher refusal. *Implemented 2026-11-02:*
   - `src/wakeCatcher.ts`, `lib/nodeWakeCatcher.ts` and `agentOps/wakeCatcher.ts`, under the capability `wake.catcher` (same owner opt-in; `NINEDEPLOY_AGENT_CONTAINER_MUTATIONS=off` also turns it off).
   - The catcher runs the agent's own image by ID as `65534:65534`, read-only, with all capabilities dropped and no published port. It has no volume or bind mount. The image declares `VOLUME /data`, which Docker would otherwise satisfy with a writable anonymous volume. The first hosted run (41511827062) caught exactly that, so `/data` is shadowed by an empty 64 KB tmpfs with mode `0555`. The smoke asserts that writes to `/data`, `/` and `/app` fail. Removal uses `rm -fv`.
   - Service containers share the proxy network, so demand counts only when a request carries the node's wake key. The `x-nd-wake-key` header is added by the panel-rendered Traefik middleware, and the key comes from `wake.catcher.ensure { key }`. The container gets it in its environment, and its label holds only a hash. Any other request gets a 404 and writes no line.
   - It writes at most one `ND-WAKE` line per token per second and 20 a second in all. `wake.demand` aggregates those lines from the catcher's Docker log since a cursor. A read that fills the 2,000-line tail is flagged `truncated`, so the panel never treats it as all the demand.
   - A missing, stopped or unlabelled catcher is refused rather than reported as no demand, and a same-name container it did not create is never touched.
   - Hosted check: `scripts/smoke-wake-catcher.mjs` in CI and on the release image.
3. Panel: the node idle clock in the sleep tick, using the idle watch. Report hold reasons (capability, coverage, opt-in) through sleep status. Never sleep on unavailable coverage. *Read-only scheduling, transport and coverage calculation implemented 2026-11-02; public status and runtime effects remain open:*
   - `lib/nodeIdleWatchClient.ts` uses the shared sealed observation client with its own idle schemas, capability and receipt frame. It retains before/after runtime, owner, route, topology and conflict checks, cancellation cleanup, source continuity and one-use finalization. Idle windows do not enter the autoscale receipt ledger.
   - A normal node deployment does not require autoscale spare capacity to be observed. Its serving names/count/port and database placement are checked in the panel; the sealed agent verifies the live immutable serving IDs and deployment labels. RPS observations still require their complete capacity receipt.
   - `lib/nodeIdleCoverage.ts` accepts only completed zero-request windows. A chain requires overlapping sequence markers, unchanged source/proxy/epoch, serving IDs, routing and runtime context. A gap, traffic, replacement, lease loss or validation failure resets coverage.
   - Chained durations are not added together: monotonic panel timestamps bracketing each opening RPC give a conservative union-duration lower bound. Opening latency and overlapping seconds cannot inflate the idle proof. Repeated and superseded completions are refused, with exact uint64 counter comparisons.
   - `lib/nodeIdleWatchService.ts` resolves all serving members through sealed `docker.identity` before opening each window. Both `docker.recovery` and `proxy.idleWatch` are required. Runtime owner/configuration checks surround discovery, and the bound transport rechecks deployment, topology and route eligibility before reserving any window.
   - `lib/nodeIdleScheduler.ts` samples every 15 seconds independently per service. It opens a successor before finishing its predecessor, resets on traffic/refusal/lease lapse, closes ineligible or superseded generations, and aborts/cleans up during server shutdown, including late opening replies. One slow node cannot block another service's lease tick. Missing current service state discards all coverage.
   - Each node reserves paired slots for at most eight active services within the agent's sixteen-window limit. Other services report capacity waiting with no idle value. Backing-off failures do not reserve empty slots or starve healthy services. Refusals retry after one minute instead of generating a request and warning at every lease tick.
   - `plugins/sleeper.ts` starts the node read-only observer separately from the existing one-minute panel-host sleep tick. The scheduler's internal status distinguishes unavailable coverage (`idleMs: null`), a verified traffic reset (`idleMs: 0`) and a completed idle proof. `idleSatisfied` is observation evidence, not mutation authority. Public status, wake reachability, route changes and runtime mutation effects remain pending; node sleep stays refused until those steps and hosted acceptance pass.
   - Transport/coverage foundation validation: 222 server tests passed in ten files covering idle transport/coverage, existing RPS observation/consumption/sample/controller/admission, agent idle watch and the Swarm runtime-reader inventory. Server typecheck and targeted lint passed. Agent transport is mocked in panel adapter tests; the agent idle tests use the real observation engine with a fake Docker I/O boundary. This is local source validation, not hosted node sleep/wake acceptance. Local Docker was not accessed (`DOCKER_HOST=tcp://127.0.0.1:9`).
   - Scheduler/helper validation: 230 focused tests passed in eleven server files, including the real Fastify plugin's 15-second cadence and shutdown. Scheduler tests use the actual idle-watch engine, counter and coverage calculator with fake Docker I/O; they verify five-minute continuous coverage, pending unverified tails, traffic, lease/source loss, late replies, concurrency, paired capacity and refusal backoff. Identity tests use migrated SQLite, real panel/client checks and a fake sealed-agent boundary. These checks do not accept real node sleep or wake effects.
4. Panel: the node sleep effect (decision 5), with its routing render for sleeping node domains pointing at the catcher with the domain middlewares kept. *Durable authority foundation implemented 2026-11-02; runtime effects remain disabled:*
   - Migration `0120_node_sleep_transitions` records the selected immutable serving IDs, runtime owner, configuration binding, idle evidence, wake token, catcher identity, ordered phase and a millisecond worker lease. It survives deletion of deployment history and is removed with the service.
   - The scheduler issues opaque, one-use idle evidence, valid for less than 30 seconds. Traffic, lost coverage and changed sources revoke outstanding evidence. Sleep admission rechecks the selected generation, routes, database placement, conflicts and current configuration transactionally; a caller-provided numeric idle value cannot admit sleep.
   - `lib/nodeSleepAuthority.ts` owns admission, checkpoints, phase transitions and exact immutable target receipts. Recovery retains the original command identity and replaces only the expired worker lease. Expired unpublished idle evidence is abandoned instead of putting the service to sleep after a restart.
   - A fresh wake demand must match the current sleeping token, node and catcher. Explicit Stop, Restart, deploy and limits supersede sleep/wake; autoscaling and automatic Start hold. Catcher recreation uses a current-owner identity comparison so an older catcher cannot wake a superseded cycle.
   - A persisted fallback-routing intent is retained when an explicit command supersedes a partially published sleep. This is journal state only: the renderer and lifecycle recovery still need to consume it and restore app routing only after readiness and routing acknowledgement. The new authority is not connected to container mutations, route publication or the wake poller, and the existing node sleep refusal remains in place.
   - Related server validation passed 338 tests in thirteen files without coverage; the database package passed all 77 tests in 31 files. A separate-process SQLite case proves worker recovery and rejection of the old worker. Server typecheck passed. An earlier combined Windows run ended with native worker exit `3221225477`; the isolated scheduler and serialized thirteen-file rerun passed, but the native failure's cause is unresolved. These checks are not full release certification or hosted sleep/wake acceptance. Local Docker was not accessed.
5. Panel: the wake poller and wake effect (decision 4), with deploy/Stop/Restart supersession and Stop arriving during a wake.
6. Surfaces: lift the node refusal in `sleepHoldReason`, the service API validation and the panel/CLI copy, but only for nodes that confirm both capabilities. Older agents keep the refusal.
7. Hosted smoke (`smoke-node-canary.mjs --sleep-only`) on isolated daemons:
   - an idle service sleeps after the window;
   - a request through the node proxy wakes it, and the reloaded page is served by the app;
   - a basic-auth domain asks for credentials before waking;
   - a request during the idle window prevents sleep;
   - agent opt-in off never sleeps;
   - Stop during a wake leaves the service stopped.

   Run it in CI and on the release image before node sleep is enabled.
